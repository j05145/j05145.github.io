## Start With the URLs, Not the Login Form

On internal assessments, back-office web apps are some of the most rewarding targets. They are built for a small set of employees, they sit "safely" behind the corporate network, and they rarely get the same scrutiny as the public website. A very common shortcut in these apps is to protect the **login page** and assume everything behind it is only reachable by people who passed through it.

My first move on any app with a login wall is to ignore the wall. I collect every path I can find (from JavaScript, sitemaps, links in error pages, wordlists tuned to the framework) and request them directly with no session. If an inner page renders, authentication is a UI flow, not a control.

## Background

During an internal network assessment for a financial-sector client, I found a back-office "one-stop window" application used by staff to process customer requests. Its landing page asked employees to sign in with their Active Directory account. Everything about it looked like a normal, protected internal tool.

<Concept>
**Forced browsing** means requesting a resource directly by its URL instead of navigating to it through the interface. It is the simplest test for **broken access control**: if the server only checks your identity at the front door (the login page) and not on each request, then knowing the address of an inner page is enough to open it.
</Concept>

## Step 1: Skipping the Front Door

Without signing in, I requested one of the application's inner pages directly (requests below are simplified, with paths and hosts generalized):

```http
GET /Documents HTTP/1.1
Host: backoffice.internal
```

There was no redirect to the login page and no error. The full application rendered, including the navigation bar with every module: transactions, payments, pending items and an **Administer** menu.

The page itself was a document list for customer transactions: submitted request forms, company bylaws and copies of personal identity documents, each one with a link to open the PDF. All of it was readable by anyone on the network who knew, or guessed, a URL.

## Step 2: The Admin Menu

The **Administer** menu had three options: unlock a user, view temporary data, and **change a user's password**. That last one is where an access control issue turns into account takeover.

The password change form asked for two things: the user's email and the new password. It did not ask for the current password, did not require a reset token sent to the user, and, because I never logged in, it obviously did not check that the caller was an administrator.

```http
POST /Administer/ChangePassword HTTP/1.1
Host: backoffice.internal
Content-Type: application/x-www-form-urlencoded

email=<victim@company>&newPassword=<chosen-password>
```

I set a new password for a test target and then used it on the real login page. The sign-in worked, and I was inside the application as that user, with that user's permissions.

<Concept>
A password change function needs **two** checks: that the caller is allowed to use the function at all (authorization), and that the caller has proven they own the account, or is an administrator acting on it (verification). This one had neither. Combined with the forced browsing issue, the only thing an attacker needed was a valid email address, which in an AD-backed app usually follows a predictable pattern.
</Concept>

## Step 3: What the Accounts Could See

Once logged in as a regular user, the transaction views showed partial payment card data (card BINs). On their own those are not a full card number, but they confirmed the takeover led straight into payment-related data and not just into an empty account.

## What Was Demonstrated

- Inner pages and the customer documents behind them were reachable with no session
- The password change function was reachable with no session and only required an email
- A password set this way worked on the real login page
- The resulting session exposed views with partial card data

## Impact

- **Unauthenticated access** to the internal back-office and the customer documents it stores (personal IDs, company records, request forms)
- **Account takeover of any user** knowing only their email address
- **Exposure of partial payment card data** through the views available to those accounts

## Remediation

- **Enforce authentication and authorization on every request**, centrally (middleware or a global filter), not on the login page only
- **Redesign the password change flow**: require the current password for self-service changes, and restrict administrative resets to authenticated administrators, with the reset delivered through a verified channel
- **Notify users** whenever their password changes, and log every administrative reset
- **Test with no session**: add an automated check that requests every route without a cookie and expects a redirect or a 401
